# 离线转写性能修复与验证记录

日期：2026-11-13（Asia/Shanghai）。

本文记录采用峰值门控、共享 PCM 队列和两份模型的历史构建。下文的代码路径、长测命令和结果均对应当时的实现。

静音跳过、每窗口输出上限和过期任务取消已实现，最终构建及常规回归测试 18/18 通过。最终真实模型长测正常完成十个阶段，每路输入 600 秒音频，进程退出码为 0。

**功能长测通过，但整机流畅性仍有限制。** 静音和低幅噪声确实零推理，双路没有失败或积压失控；进程物理占用峰值约 2.40 GiB，卸载后降至约 73 MiB。然而测试期间仍出现一次约 1.19 秒的 Metal 帧提交间隔和明显系统交换活动，不能宣称“整机已不卡”。

## 问题与修复

用户反馈：开始实时转写后整机卡顿，卸载引擎后似乎恢复。排查发现，原实现会把双路静音持续送入一秒窗口识别；每个窗口沿用模型默认的 512-token 输出上限；关闭或超时后，排队任务只在推理完成回调中检查是否过期。

本次修复如下：

| 项目 | 实现行为 | 验证重点 |
| --- | --- | --- |
| 静音门控 | 按最多 10 ms 的 PCM16 音频片段检查峰值。空闲时峰值不超过 400 的音频只保留最近 300 ms，不调用模型；检测到声音后补入前置音频。 | 持续静音和低幅噪声不进入推理，语音起点保留。 |
| 断句与尾音 | 安静达到一秒时结束当前句，只向模型补入 200 ms 尾音；不足一秒的停顿在声音恢复时完整保留。停止时也冲刷有限尾音。 | 断句前后顺序不变，短暂停顿不被删除，大包可包含多个句段。 |
| 输出上限 | 每次流启动和重启都同时设置 `audio_chunk_seconds=1.0` 与 `max_tokens=64`。设置失败时不启动该流。 | 两路和重新开始均使用上限，错误路径不继续推理。 |
| 过期任务取消 | 关闭、重新测试、来源失败、队列间断和停止超时使对应来源的取消令牌失效；工作线程在执行前检查令牌。 | 排队但未开始的 push/finish 不再调用引擎；超时后旧采集音频不能通过新令牌重新进入推理。 |
| 停止状态 | finish 计数按来源及当前 epoch 管理；最后一个来源失败并完成排空时结束停止状态。 | 旧回调不污染新会话计数，不产生额外的五秒超时。 |

模型推理继续在同一个工作线程上串行执行。当前仍保留 MIC、SPK 两份模型及两套 GPU 会话，本次没有修改权重共享机制。

关键代码：`src/app/offline_audio_gate.h`、`src/app/offline_transcription_controller.cpp`、`plugins/OfflineTranscription/offline_transcription_engine.cpp`。

## 长测协议

`offline_transcription_soak_tests` 使用真实控制器、双路共享 PCM 队列、打包的 audio.cpp 和真实 GPU 模型。测试先记录未加载基线，再加载模型、记录加载后空闲状态，之后按实时节奏执行以下十个阶段，每阶段 60 秒，共为每路输入 600 秒音频：

| 顺序 | 阶段 | 目的 |
| --- | --- | --- |
| 1 | 初始静音 | 验证双路零推理、零胶囊、零待处理音频。 |
| 2 | 低幅噪声 | 验证门控阈值内噪声被跳过。 |
| 3 | 双路语音 | 观察正常识别、积压和资源占用。 |
| 4 | 可闻噪声 | 让噪声进入真实解码，检验输出上限后的负载。 |
| 5 | 语音混合噪声 | 观察噪声背景下的连续识别。 |
| 6 | 语音／静音切换 | 每四秒切换，验证多次开门、断句和复用。 |
| 7 | 静音恢复 | 观察持续推理是否停止及缓存占用。 |
| 8 | 再次可闻噪声 | 对照首次噪声阶段，观察是否累积退化。 |
| 9 | 再次双路语音 | 对照首次语音阶段。 |
| 10 | 最终静音 | 验证恢复空闲，随后排空、卸载并记录恢复。 |

应用每秒记录物理占用、累计 CPU 时间、两路待处理字节、推理调用次数及耗时、胶囊数量和 50 ms Qt 心跳延迟。推理调用包含小块入流与 finish，其中不是每次调用都会触发完整模型解码，因此不能把“调用数”直接解释为“识别窗口数”。

可选的置顶 Qt Quick 动画窗口使用 Metal，记录 `afterFrameEnd` 提交间隔；独立 Python 观察进程记录系统交换、压缩、解压、内存压力和 50 ms 调度探针延迟。帧提交间隔不等于 GPU 完成时间或实际屏幕呈现间隔。

保护条件只终止此次测试子进程，不操作其他应用。进程物理占用上限默认为 4,096 MiB；连续严重调度停顿、内核 critical 内存压力及持续超过配置值的系统 swap 增长也会终止测试。较早尝试使用 1,536 MiB swap 增长阈值；后续尝试记录为 3,072 MiB，仍保留其他保护。放宽阈值不会把已经发生的交换增长算作通过证据。

最长的 1,189.10 ms 帧提交间隔出现在 11:28:02 左右的可闻噪声阶段，同时 Qt 心跳延迟达到 1,145 ms。相邻约 1.15 秒的系统采样区间记录到 **547.92 MiB swap-in、359.31 MiB swap-out**。时间上重合支持进一步调查内存压力，但不能证明这次帧停顿完全由模型或交换造成。初始静音和静音恢复阶段在零推理时也分别出现 445.03 ms、627.07 ms 的最大帧提交间隔。

因此本轮结论是：**三项修复的功能行为和十分钟双路持续运行已验证；无效静音推理已消除，队列与进程物理占用保持有界，但此台 8 GiB 日常桌面环境仍存在明显内存压力与偶发响应停顿。** 后续降低双模型常驻内存的收益值得单独评估，不能用本次功能通过替代“整机不卡”的验收。

## 结论边界

1. 音频由测试程序注入，未覆盖实际麦克风和系统声音设备的现场采集。
2. 心跳、调度和动画提交是响应性的客观代理指标，不能单独证明整个桌面的主观操作体验完全流畅。
3. 简单能量门控只能跳过低幅音频；较响噪声会进入模型，安静语音也可能受固定阈值影响。它不是语音／噪声分类器。
4. 当前 C ABI 不暴露可靠的生成 token 数或停止原因，无法将达到 64-token 上限的输出单独标记为截断。测试也不证明噪声识别准确或不存在幻觉。
5. 已经开始的原生推理不能被此 ABI 中断；取消修复针对未开始的过期任务。模型卸载仍须等待正在执行的调用返回。
6. 两套模型权重仍常驻。静音跳过主要减少无效推理，不能预期它把双路加载内存自动降为一套模型。
7. 没有在同一桌面负载下运行完整的修复前／修复后配对长测，不能给出整体性能提升百分比。
